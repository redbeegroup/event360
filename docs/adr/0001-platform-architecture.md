# ADR-0001: Event 360 Platform Architecture & Project Plan

Status: Accepted (2026-11-18)


## Context
Event 360 is a new event ticketing and management platform for the Myanmar market. The repository (`redbeegroup/event360`) is empty, so this is a new build. The platform has five parts:

- **Event 360 User app** (Flutter, iOS and Android): browse and search events by category, view event details, register for free events or buy tickets for paid ones, and keep a ticket wallet with QR codes.
- **Organizer app** (Flutter): manage your own events on the go, see sales and check-ins, and send announcements.
- **Event Crew app** (Flutter): scan QR tickets (including offline), see live attendance counts, sell tickets at the door, and see shifts and task assignments.
- **Web portal** (Next.js): an admin console for the platform operator and a full organizer back-office.
- **Backend** (NestJS) running on the existing Kubernetes cluster, using the external PostgreSQL cluster.

Payments are in MMK. Each provider is integrated directly: KBZPay, WavePay, CB Pay, AYA Pay, MPU (separate API), and Visa/MasterCard/JCB/UPI cards through the CB Bank MasterCard gateway (MPGS).

Revenue comes from four sources, all of which must be configurable:
- a commission on each paid ticket,
- a subscription per organizer,
- a subscription per event, and
- **paid Featured-event placements**.

Events can be held **in person, online (live stream), or hybrid**, and **recorded sessions** can be watched afterwards, either free or paid. Live and recorded video is stored on your own S3-compatible storage (**SeaweedFS**).

Event categories are managed by the admin, with two levels:

| Category | Sub-categories |
|---|---|
| Lifestyle & Social | Food & Beverage Fair, Fashion Shows, Art Exhibitions & Galleries, Meet & Greet |
| Entertainment & Culture | Concerts & Music Festivals, Musicals, Cultural Festivals |
| Conference | Seminars, Conferences, Summits |
| Education & Business | Workshops & Training, Networking Events |

## 1. Architecture

```
 Flutter: user_app / organizer_app / crew_app        Next.js web (admin + organizer)
                 │  HTTPS/JSON (OpenAPI)  + WebSocket (live counts)
                 ▼
   ┌──────────── Kubernetes (ingress-nginx + cert-manager) ─────────────┐
   │  api (NestJS, HPA)   realtime (Socket.IO gateway)   worker (BullMQ)  │
   │  web (Next.js SSR)   Redis (cache/queues/locks)                      │
   │  STREAMING: SRS ingest (RTMP/SRT) → transcoder (FFmpeg, ABR ladder)   │
   │             → HLS/LL-HLS packager → playback-edge (nginx cache +      │
   │             token auth)  ·  vod-worker (recording → VOD HLS)          │
   │  Observability: Prometheus, Grafana, Loki, OpenTelemetry → Tempo    │
   └───────────────┬───────────────────────────┬─────────────────────────┘
                   │                           │ S3 API
                   │                 SeaweedFS (your cluster): buckets
                   │                 media/, live/, vod/, recordings-raw/
                   │ PgBouncer (in-cluster) → external PostgreSQL primary (+ read replica for reports)
                   │ egress → KBZPay / WavePay / CB Pay / AYA Pay / MPU / CB MPGS, FCM, SMS, SMTP
```

**Architecture style: a modular monolith.** There is one NestJS codebase with strict module boundaries. It is deployed as three workloads from the same image:

- `api`: the HTTP API.
- `realtime`: the WebSocket gateway.
- `worker`: queues and cron jobs such as payment reconciliation, notifications, payouts and hold expiry.

Starting as one codebase keeps operations simple. Payments or ticketing can be split into their own services later if load requires it.

## 2. Backend modules (apps/api/src/modules)

| Module | Responsibility |
|---|---|
| `auth` | Sign-in by phone OTP (the main method in Myanmar), email/password, and Google/Facebook. JWT access tokens with rotating refresh tokens. Device registration for push notifications. |
| `users` | Profiles, language preference (Myanmar Unicode or English), saved/followed events and organizers. |
| `organizations` | Organizer accounts (multi-tenant), KYC documents, bank and wallet payout details, members and their roles. |
| `rbac` | Roles: `consumer`, `org_owner`, `org_manager`, `org_finance`, `crew`, `platform_admin`, `platform_finance`, `support`. Guards check permissions for each organization and each event. |
| `catalog` | Admin-managed categories (two-level tree), tags, venues and cities. |
| `events` | Event lifecycle: draft → submitted → approved/rejected → published → ongoing → completed/cancelled. Holds sessions and dates, media gallery, venue/map, terms and FAQ. Supports free and paid events and public or private (invite link) events. |
| `ticketing` | Ticket types (price, quota, sales window, per-order limit), promo codes, and inventory **holds**. Holds use an atomic `UPDATE ... SET held=held+n WHERE sold+held+n<=quota` with a TTL that the worker releases. Issues tickets and supports transfers. |
| `orders` | Cart → order (`PENDING_PAYMENT` → `PAID` / `EXPIRED` / `FAILED` → `REFUNDED`). Free orders go straight to `CONFIRMED`. Supports idempotency keys. |
| `payments` | A `PaymentProvider` interface with one adapter per provider (§3). Handles webhooks/callbacks, signature verification, polling reconciliation and refunds. |
| `ledger` | A double-entry ledger in MMK, stored as integer amounts. For each sale it records gross, provider fee, platform commission and organizer payable. This is the single source of truth for settlements. |
| `billing` | The fee engine and subscriptions (§4). |
| `payouts` | Settlement statements per event and per period, payout batches, and the approval flow for finance staff. |
| `checkin` | Signed QR tickets, gate scans, an offline manifest for crew, sync of offline scans with conflict resolution (the first scan wins and duplicates are flagged), and live counters held in Redis and broadcast over the WebSocket. |
| `crew` | Crew invitations per event, shifts, gate/zone assignments, tasks and incident reports. |
| `pos` | Door sales from the crew app: cash, a QR payment shown on screen, or card through the MPGS hosted page. These sales are tied to the crew member's shift for cash reconciliation. |
| `notifications` | Push (FCM, which also delivers to iOS via APNs), SMS through a local aggregator, email, and an in-app inbox. Supports templates in both languages, organizer broadcasts to ticket holders, and event reminders. |
| `search` | PostgreSQL full-text search plus `pg_trgm`. Filters: category, date, city, free/paid, price range. Search can move to Meilisearch later if needed. |
| `media` | Presigned uploads to MinIO/S3 and image resizing in the worker. |
| `reports` | Sales, attendance, revenue and payout reports. Reads from the replica and exports to CSV/XLSX. |
| `audit` | Append-only audit log of admin, finance and organizer actions. |
| `cms` | Home page banners, editorial picks and static pages. |
| `streaming` | Live channels for each event session, organizer stream keys, ingest webhooks (on_publish/on_unpublish), stream health, and the live/ended state. Issues playback tokens and limits concurrent sessions. Live chat, Q&A and polls go through the realtime gateway. (§6a) |
| `vod` | Recordings: the processing pipeline, an availability window (for example 30 days after the event), chapters/trim, and pay-per-view or bundled access. Uploading a pre-recorded video is also supported. |
| `entitlements` | One place that answers "can user X attend in person / watch live / watch the recording of event Y?". Answers are derived from tickets, free registrations and purchases, and are cached in Redis. |
| `promotions` | Paid Featured-event placements: slot inventory, booking, payment, approval, ranking and analytics. (§4a) |

## 3. Payment integration design

**Common interface:** each provider adapter implements the same interface:

```ts
interface PaymentProvider {
  code: 'KBZPAY'|'WAVEPAY'|'CBPAY'|'AYAPAY'|'MPU'|'CB_MPGS';
  createPayment(order, ctx): Promise<{ type:'DEEPLINK'|'QR'|'REDIRECT'|'IN_APP_SDK'; payload; providerRef }>;
  verifyCallback(headers, body): Promise<VerifiedEvent>;   // signature/HMAC check
  queryStatus(providerRef): Promise<PaymentStatus>;          // for reconciliation
  refund(payment, amount): Promise<RefundResult>;
}
```

**Payment flow:**
1. The user picks tickets. The API creates a 10-minute hold and a `PENDING_PAYMENT` order.
2. The app chooses a payment method. `createPayment` returns one of:
   - a deeplink to the wallet app (KBZPay, WavePay, AYA Pay, CB Pay),
   - a QR code (for the crew door-sales screen or the web portal), or
   - a hosted checkout page (MPU, CB MPGS) shown in a WebView or browser.
3. The provider calls the provider-specific webhook endpoint, `/payments/webhook/:provider`. The API verifies the signature, stores the raw payload in `payment_events`, and processes it idempotently by provider reference. It then:
   - marks the order `PAID`,
   - converts the hold into sold tickets,
   - writes the ledger entries, and
   - sends the e-ticket by push, SMS or email.
4. **Reconciliation worker:** every minute it polls `queryStatus` for pending payments, because Myanmar wallet callbacks are not always reliable. When a hold expires it marks the order `EXPIRED`. A late success after expiry triggers an automatic refund, or a manual review if no inventory is left.
5. **Daily settlement:** the provider settlement files and reports are compared against the ledger. Mismatches are shown in the admin finance screen.

**Security and compliance:**
- Provider credentials are stored in Kubernetes Secrets through External Secrets or Sealed Secrets.
- Card data never touches our servers: the MPGS hosted checkout keeps us at PCI SAQ-A scope.
- Every amount is in MMK and stored as an integer.

**Provider rollout order** (each provider is a separate milestone so no single bank's API timeline blocks launch): KBZPay → WavePay → CB MPGS (cards) → MPU → AYA Pay → CB Pay.

## 4. Revenue / billing engine

- **`fee_rules`** define the commission as a percentage plus a fixed MMK amount, optionally with a minimum and maximum. A rule is scoped to one of: global default → category → organization → event, and the most specific rule wins. A rule also says who absorbs the fee: either the buyer pays it on top of the price, or it comes out of the organizer's revenue.
- **`plans`** hold subscription plans, with `scope = ORGANIZER | EVENT`, a price and billing period, and limits. Example limits: maximum published events, maximum tickets, number of crew seats, access to featured placement, and the commission rate that applies under the plan. For example, a Pro plan could lower the commission.
- **`subscriptions`** record which plan each organization or event is on. Organizers pay for subscriptions through the same payment providers. A per-event subscription must be paid before the event can be published. The worker sends renewal and expiry reminders.
- At checkout the fee engine fixes the applicable fee on the order. Later rule changes therefore never alter past orders.
- Free events: there is no commission. A per-event plan can still be required, for example for large free events.
- Plans can also include **streaming quotas**, for example how many live hours, maximum concurrent viewers, recording storage in GB, and how long recordings are kept. Usage above the quota is billed per viewer-hour or per GB-month, so streaming cost (bandwidth and storage) is passed on to the organizer.

## 4a. Featured events (paid promotion)

**Placements** (admin-configurable). Each has a capacity of slots per day and a price per day in MMK:
- `HOME_HERO`: the home page carousel.
- `HOME_FEATURED_ROW`
- `CATEGORY_TOP`: per category or sub-category.
- `SEARCH_BOOST`: pinned at the top of matching searches.
- `CITY_TOP`
- `PUSH_BLAST`: one push notification to opted-in users in the target city or category, with daily frequency caps.
- `ORGANIZER_SPOTLIGHT`

**Booking flow:**
1. The organizer picks the event, the placement, the date range, and optionally the city or category to target. The portal shows a live availability calendar for that placement.
2. A price quote is calculated from the base rate, multiplied by any demand multiplier for peak dates, minus any discounts included in the organizer's plan.
3. The organizer pays through the same payment providers. The slot is held for 10 minutes while payment completes, using the same hold mechanism as tickets.
4. An admin reviews the creative (banner image and copy) and approves it.
5. The placement goes live and ends automatically on schedule.
6. Refunds follow the policy: a full refund if the admin rejects the creative, and a pro-rata refund if the event is cancelled.

**Delivery:**
- The `promotions` service returns the active placements for each surface.
- The app shows a "Featured" label on these events.
- When more bookings than slots exist (for example in a carousel), they rotate fairly.
- The service records impressions, clicks and conversions (ticket sales attributed within 7 days). The organizer sees ROI on the web portal and in the organizer app.

**Accounting:** placement revenue is recorded in the ledger as platform income, kept separate from ticket commission.

**Tables:** `promo_placements`, `promo_rate_cards`, `promo_bookings`, `promo_creatives`, `promo_metrics_daily`.

## 5. Core data model (PostgreSQL, Prisma)

The schema is managed by Prisma migrations. Main tables:

- **Users and organizations:** `users`, `user_identities` (phone, email, OAuth), `devices`, `organizations`, `organization_members`, `organization_kyc`, `payout_accounts`
- **Catalog and events:** `categories` (parent_id), `venues`, `events`, `event_sessions`, `event_media`, `event_categories`
- **Tickets and orders:** `ticket_types`, `promo_codes`, `inventory_holds`, `orders`, `order_items`, `tickets` (qr_nonce, status, holder_user_id)
- **Payments and money:** `payments`, `payment_events` (raw webhooks), `refunds`, `ledger_accounts`, `ledger_entries`, `fee_rules`, `plans`, `subscriptions`, `invoices`, `payouts`, `payout_items`
- **On-site operations:** `checkins` (ticket_id, gate, device, crew_id, scanned_at, offline bool), `crew_assignments`, `shifts`, `tasks`, `incidents`, `pos_sessions`
- **Engagement and admin:** `notifications`, `notification_templates`, `favorites`, `follows`, `reviews` (post-event), `audit_logs`, `cms_banners`
- **Streaming and video:** `live_channels` (session_id, stream_key_hash, ingest_url, status), `live_sessions` (start, end, peak_viewers), `recordings`, `vod_assets` (renditions, duration, s3_prefix, availability window, price), `playback_sessions` (user, device, started_at, last_heartbeat, watch_seconds), `entitlements`, `chat_messages`, `qa_questions`, `polls`
- **Featured promotions:** the `promo_*` tables listed in §4a
- **Ticket delivery mode:** `ticket_types.delivery_mode` is one of `IN_PERSON | LIVE_ONLINE | RECORDING | BUNDLE`, and `events.format` is one of `IN_PERSON | ONLINE | HYBRID`

**Conventions:**
- Primary keys are UUIDv7.
- Every row has `created_at` and `updated_at`.
- Money columns are `bigint` MMK.
- Domain tables that need to keep history use soft delete.

**Database cluster setup:**
- Separate databases or roles per environment.
- PgBouncer in transaction mode inside the cluster.
- A read-only role for reports.
- Point-in-time recovery (PITR) backups, managed on your existing DB cluster.

## 6. QR tickets & offline check-in

- The QR code contains a compact signed token (Ed25519): `{tid, eid, tt, v}` plus a signature. The private key stays on the server. Crew apps receive the public key.
- **Before the event**, the crew app downloads that event's manifest: ticket IDs, their status, and the ticket-type and gate rules. The manifest is encrypted at rest with the device key.
- **Scanning:**
  - The app verifies the signature locally, checks the ticket against the manifest, and checks its local scan log for duplicates. It gives instant green/red feedback.
  - When online, the scan is also posted to the server.
  - When offline, scans are queued and synced later. The server marks the earliest scan as authoritative and flags the others as duplicates.
- **Live counters** are kept in Redis per event, gate and ticket type. They are pushed over WebSocket to the organizer app, the crew app and the web portal.
- **User app wallet:** tickets are stored locally so they still show without a network connection. The QR code refreshes its `v` value when a ticket is transferred, which invalidates the old QR.

## 6a. Live streaming & recorded sessions

**Video stack.** Everything below runs in Kubernetes (the `event360-media` namespace) and stores video on your SeaweedFS:
- **Ingest:** SRS (Simple Realtime Server).
  - The organizer streams with OBS or vMix, or a hardware encoder, over RTMP or SRT to `ingest.event360.app/live/<channel>?key=<streamKey>`.
  - The SRS `on_publish` hook calls the API to validate the stream key and session time window.
  - A TCP/UDP LoadBalancer Service exposes ports 1935 (RTMP) and 10080/udp (SRT).
- **Transcode:** an FFmpeg transcoder pod per live channel, launched by the `streaming` module as a Kubernetes Job.
  - It produces an adaptive bitrate ladder: 1080p (optional, depends on the plan), 720p, 480p and 360p, plus a 240p rendition for low-bandwidth Myanmar mobile users.
  - Output is HLS with 2-second segments (LL-HLS optional later). Latency is about 6–10 s.
- **Storage:** segments and playlists are written to SeaweedFS under `live/<channel>/` through the S3 API. A lifecycle rule cleans up live segments after they are copied into the recording.
- **Delivery:** `playback-edge`, an nginx deployment with a proxy cache in front of the SeaweedFS S3 gateway.
  - It checks access with the `secure_link` module: an HMAC token with an expiry in the URL. The API issues this token after the entitlement check.
  - It runs with HPA. A CDN can be placed in front later, for example a local Myanmar CDN or Cloudflare. Tokens still work because they are carried in the URL.
- **Recording:**
  - When the stream ends (`on_unpublish`), the vod-worker builds the VOD from the live HLS segments, with no re-encode needed.
  - It stores the VOD under `vod/<asset>/`, generates thumbnails and an MP4 download (optional, organizer-controlled), and marks the asset `READY`.
  - Organizers can trim, add chapters, or upload a pre-recorded file. Uploads go to SeaweedFS directly with a presigned multipart upload, and the vod-worker then transcodes them to HLS.

**Access control and anti-piracy:**
- HLS content keys use **AES-128 encryption**. The key URL points to the API `/streaming/keys/:asset`, which serves the key only with a valid entitlement and playback token.
  - This raises the effort needed to pirate content without the cost of DRM. Widevine/FairPlay DRM can be added later for premium content.
- **Concurrent stream limit:** one active stream per ticket by default.
  - The player sends a heartbeat every 30 seconds, tracked in Redis.
  - A new device starting playback stops the old one, with a message to the user.
- **Visible watermark:** a dynamic overlay of the user's masked phone number or ID in the Flutter and web players.
- **Short token TTL:** tokens last about 5 minutes and the player renews them automatically.

**Monetization options per event** (set as ticket types):
- *Live online ticket*: watch the live stream only.
- *Recording pass*: pay-per-view for a recorded session after the event, with a set availability window.
- *Bundle*: in-person + live, or live + recording.
- *Free live*: requires registration so the platform can capture leads for the organizer.

All of these go through the same order, ledger and commission flow as normal tickets.

**Viewer experience (User app and web):**
- A "Watch" tab in My Tickets, and live badges on event cards.
- The player is `better_player_plus` or `media_kit` in Flutter, and hls.js on the web.
- Viewers can pick quality, use picture-in-picture, keep audio playing in the background, see live chat, ask questions in Q&A with upvotes, and answer polls.
- Recordings show chapters and remember where the viewer stopped.
- Online events can also be watched on the web portal (`watch.event360.app`) so viewers on desktop are covered.

**Organizer tools:**
- In the web portal: the stream key and ingest URL, a test-stream preview, live health (bitrate, frames dropped, viewers), moderation of chat and Q&A, start/stop recording, and VOD editing.
- In the organizer app: live viewer counts and stream health.
- The crew app can act as a chat/Q&A moderator.

**Capacity sizing (starting point):**
- Each 720p ABR transcoder needs about 2–4 vCPU. A dedicated node pool for `media` is recommended, optionally with GPU/NVENC later.
- Bandwidth is the main cost: 1,000 viewers × 1.5 Mbps ≈ 1.5 Gbps.
  - Plan the edge egress capacity, and add a CDN when an event will have more than about 2–3k concurrent viewers.
  - Charge streaming above the plan quota to organizers, as in §4.

## 8. Kubernetes & DevOps

> **Updated 2026-11-18 to match the actual cluster.** The original draft assumed ArgoCD, cert-manager and ingress-nginx; none of them are installed.

- **Cluster:**
  - Talos Kubernetes 1.36 (3 control-plane nodes, 4 workers with 8 vCPU / 8 GB each), managed through Portainer EE.
  - MetalLB; storage classes `synology-iscsi` (block) and `synology-nfs`.
- **Edge:**
  - NPMPlus terminates TLS for `*.event360.app` and `*.dev.event360.app`.
  - It forwards to Traefik at `172.16.16.180:80` (ingress class `traefik`). See `docs/npmplus-setup.md`.
- **Environments:**
  - `event360-dev` and `event360-prod` share PostgreSQL database `event360` on the external cluster (`172.16.16.39:5433`), one schema each (`dev`, `prod`).
  - They share SeaweedFS bucket `event360`, one prefix each.
  - Separate databases and buckets for staging/prod can come later. Only `DATABASE_URL`/`S3_*` in the Secret change.
- **Deployment (Portainer GitOps):**
  - `infra/manifests/generate.mjs` renders plain manifests to `deploy/<env>/event360.yaml`, and Portainer polls them from Git.
  - CI builds images to `ghcr.io/redbeegroup` (public packages) on every push. On `main` it pins dev to the new commit SHA.
  - Prod is promoted by PR.
- **Migrations:** an init container on `api` runs `prisma migrate deploy` (with Prisma's advisory lock) and an idempotent seed.
- **Workloads:**
  - `api`, `realtime` (sticky cookie on its Traefik service), `worker` and `web`.
  - A dedicated Redis StatefulSet (AOF, `noeviction` for BullMQ) on `synology-iscsi`.
  - PgBouncer is deferred. Prisma caps each pod at `connection_limit=5`.
- **Secrets:**
  - `event360-secrets` per namespace is created directly in the cluster through the Portainer API. It is never in Git.
  - External Secrets/Sealed Secrets can be adopted later.
- **Streaming (Phase 5b):**
  - a dedicated `event360-media` namespace;
  - RTMP/SRT exposed through a MetalLB IP or NPMPlus Streams;
  - transcoders sized against the 4×8-vCPU workers, so add worker capacity before large live events.
- **Observability (to add):** Prometheus/Grafana/Loki are not installed yet; to be decided in Phase 1.
- **CI (GitHub Actions):** Prisma validate + drift check, typecheck, unit tests, manifest freshness, image builds, and Flutter analyze/test.
- **Security baseline:**
  - rate limiting (real client IP via `TRUST_PROXY=2` and Traefik trusted IPs), Helmet, validation, OWASP ASVS L2;
  - signed media URLs, PII encryption for KYC, audit log, backup/restore drill.

## 10. Key risks & mitigations
- **Payment provider onboarding and sandbox delays.** Start merchant applications and sandbox access with all six providers in week 1. The adapter interface plus a `MockProvider` lets the rest of the build continue unblocked.
- **Overselling during on-sale spikes.** Use atomic DB holds plus a Redis rate-limit queue per event. Load test before launch.
- **Streaming bandwidth and cost.** Use a low-bitrate ladder (including 240p), enforce plan quotas, put a CDN in front for large events, and use a dedicated media node pool so transcoding cannot starve the API.
- **Stream piracy.** Short-lived tokens, AES-128 key gating, a concurrent-session limit, and a visible watermark. Add DRM later for premium content.
- **Featured-placement trust.** Every placement carries a clear "Featured" label, an admin approves each creative, and frequency caps limit push blasts.
- **Unreliable connectivity at venues.** The crew app works offline first, and the user ticket wallet works offline.
- **Myanmar text.** Unicode only, with a bundled Myanmar font (e.g. Pyidaungsu or Noto Sans Myanmar). Detect Zawgyi input and convert it (Rabbit converter) in user-entered text.

## 11. Verification (per phase and at launch)
- **Backend:**
  - Jest unit tests for the fee engine, holds, ledger balancing (debits equal credits) and QR signing.
  - Integration tests with Testcontainers (Postgres and Redis).
  - Contract tests for each payment adapter against recorded sandbox payloads.
- **End-to-end on the dev cluster:** a Playwright suite for the web portal (create event → publish → buy as user → check in → payout statement). Flutter `integration_test` for the user checkout and the crew offline scan-then-sync.
- **Payments:** a sandbox transaction matrix for each provider (success, fail, timeout, late callback, refund), then the provider's own UAT sign-off.
- **Load test:** a k6 on-sale scenario against staging. Exit criteria: no oversell, p95 under 500 ms, and the reconciliation backlog clears within 5 minutes.
- **Streaming:**
  - OBS publishes to staging ingest. Verify the stream reaches all renditions on SeaweedFS, playback works with a valid token, and an expired or missing token gets a 403.
  - Verify a second device stops the first, and that the VOD becomes `READY` within 10 minutes of the stream ending.
  - Load test with a k6 or hls-loadtest scenario: 3k viewers against playback-edge, with a cache hit ratio of 95% or higher.
- **Featured events:**
  - Book, pay, approve and go live, and confirm the placement appears in the app.
  - Confirm overbooking is prevented, the placement expires automatically, and impressions and clicks are recorded.
- **Operations:** a restore drill from a PostgreSQL PITR backup, and a chaos test of killing worker pods during reconciliation.
